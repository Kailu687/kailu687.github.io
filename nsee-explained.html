NSEE, explained simply

22 November 20265 min read

The idea in one paragraph

Most AI assistants today run on a huge neural network that does everything at once: understanding you, planning, remembering facts and writing the reply. That works, but it needs a lot of memory and, usually, the cloud. I wanted to try the opposite. What if a small, ordinary program did the thinking and the doing, and you could teach it new skills just by adding a file? That experiment became NSEE, short for Neuro-Symbolic Edge Agent. It runs offline on my laptop and the whole engine is under 1 MB of plain Python.

One honest note before we start: I built NSEE with a lot of help from AI coding assistants. I decided what it should do, tested it and measured it, and I'm still learning many of the ideas inside it. This post explains it the way I understand it.

What happens when you type a request

Let's follow one request all the way through: "sort my downloads, don't delete anything".

  • Understand. A rule-based parser (no neural network) splits the sentence into goals. "Sort" becomes something it's allowed to do, and "delete" becomes something it is never allowed to do.

  • Pick a skill. It looks through its skill files for the one that matches "sort files".

  • Fill in the details. Which folder? Group by what? It pulls these from your sentence, or uses defaults and tells you which ones it assumed.

  • Check the rules. Is anything blocked? Is a number out of range? If so, it stops and says why.

  • Ask permission. Before touching anything, it shows you exactly which files will change.

  • Do it, safely. It saves a copy of everything it's about to change, so it can undo the whole thing if something goes wrong.

The tricky word: "don't"

Big language models are known to sometimes "lose" a negation. Usually that's harmless, but if the model is also allowed to touch your files, a lost "don't" can delete something. NSEE treats negation as part of the structure instead.

The "don't" attaches only to its own part of the sentence. Then a safety gate checks every action before it runs, and refuses anything that matches a blocked word. So even a buggy skill can't delete files you protected.

It isn't perfect. On sentences built from patterns, it caught the negation 140 times out of 150. On natural ones I wrote by hand, like "no renaming" or "leave the logs alone", it only caught 28 out of 50. That's the weakest part of the project, and it's the first thing I'd improve.

Skills are just files

Every ability NSEE has comes from a "skill capsule": a JSON file with no code in it. It lists the words that call it, the settings it needs, the formulas it uses, the rules it must follow and what it produces.

My favourite example is the antenna skill. One file covers six antenna types (patch, dipole, monopole, helix, Yagi and horn) using standard textbook formulas, and it also writes a script you can open in Ansys HFSS. It understands sloppy input too, like "patch 5.8G" or "desing a dipole at 433 mhz". All 16 casual requests I tried came out right. The HFSS scripts pass a syntax check, and actually simulating them is my next step.

Never leaving a mess

A multi-step task can fail halfway, for example after renaming one file and moving another. NSEE keeps a journal so that never leaves your folder half-changed.

To test this, I generated 200 random plans, crashed each one at a random step, and checked the folder afterwards. All 200 were restored exactly, byte for byte.

Where do the "neurons" come in?

NSEE also has small simulated spiking neurons, a simplified model of how real neurons fire. They take part in choosing which kind of ability a request needs, and they slowly strengthen the connection between a request and a skill each time that skill works.

Here's the honest part. When I compared the spiking version against a plain "does this request have the right keywords?" check, on 60 test requests, they made exactly the same choices every time. So right now the neurons don't make routing better. They're an interesting piece to experiment with, not a feature I can claim works.

What I learned

A small, predictable program is great at well-defined jobs: sorting files, generating designs from formulas, solving small puzzles, and doing all of it safely and offline. It's bad at anything open-ended, like natural conversation or writing about a topic it has no source for. That still needs a real language model.

The bigger lesson for me was about honesty in engineering: measure what you want to claim, compare against something simple, and write down the failures as clearly as the wins. Some of my favourite results in this project are the ones that didn't work.
