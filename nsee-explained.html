What if AI didn't need a data centre? The story behind NSEE

22 November 202610 min read

It started with a question

AI and communication are quickly becoming lifelines for people everywhere. I honestly think that, someday, access to them should be treated as a basic right rather than a privilege.

Using tools like Claude Pro showed me how powerful AI already is. It also made me think about the people on the other side of that: people who can't afford a subscription, don't have a powerful computer, or don't have reliable internet. Why should useful intelligence always need massive data centres, expensive hardware, huge amounts of power and a monthly bill?

So I set myself a slightly crazy goal. Could I build an AI-like assistant that isn't a large language model? Not another chatbot, but something closer to a personal butler for your computer: it understands a task, picks the right tool, runs a known workflow, and never does anything you told it not to. And it had to be small: under 1 MB, standard-library Python only, offline, and ideally able to run even on an old 2 GB RAM laptop.

I called it NSEE, the Neuro-Symbolic Edge Engine. This post is the full behind-the-scenes story: what I tried, what I changed and why, and what the numbers said in the end.

One thing up front: I built NSEE with a lot of help from AI coding assistants. I decided what it should do, kept changing direction when things didn't work, tested it and measured it. I'm still learning a lot of the ideas inside it, and this post is how I understand them today.

The hypothesis: borrow a few ideas from the brain

The brain doesn't run one enormous list of instructions. It has specialised regions, neurons that fire when their input crosses a threshold, and connections that change with experience. My bet was that a few of those ideas could shape a small, efficient program. This is what each idea eventually became:

These are small, simplified software models. They borrow ideas from neuroscience; they don't simulate a brain. But having the brain as a map helped me decide what pieces the system needed.

Version 0.1 and 0.2: a parser, a few skills and some neurons

The very first version did one thing: it turned a request into steps and generated a quadcopter frame for CAD. Version 0.2 became the real core. A rule-based "intent compiler" turned a sentence into a list of goals with typed values (like "at least 3 mm"), and every goal got a polarity: allow or block. That polarity is the reason NSEE never loses a "don't":

The other big decision was to keep knowledge out of the code. A rule I gave myself early on: no gadget-specific code in the engine. Every ability lives in a "skill capsule", a JSON file with triggers, settings, formulas, rules and outputs. Adding a file adds a skill, and nothing needs retraining.

The first spiking neurons appeared here too: a small network that routes a goal to a skill and strengthens that connection every time the skill succeeds, a simplified version of how synapses strengthen with use (STDP).

First real test: it didn't understand me

The first time I used it properly, it failed on simple things. If I asked a question, it sometimes tried to do something instead. So in the next version every goal also got an intent (explain, inspect, query or change), and skills got a risk class (read, report or write). A question can never trigger a skill that writes files.

Around then I had a choice. I could add a 22 MB sentence-embedding model to understand wording better, or stay model-free. I chose to stay model-free and built a concept thesaurus plus a vocabulary the system learns from use. Keeping it tiny was the whole point.

Versions 0.4 to 0.7: making it usable

A command line isn't something normal people use, so I added a chat UI that runs locally, with a permission card before any file changes. Then I kept fixing the gaps I hit while using it:

  • Spelling. Searching "Abdul Kailam" should still find A. P. J. Abdul Kalam, so I added phonetic matching and a frequency-based spelling corrector.

  • Online knowledge. For questions it couldn't answer, an optional online mode reads Wikipedia or a web search, and can save the answer for offline use later.

  • Teaching it. You can drop a guide or a cheat-sheet into it, and it turns the steps and formulas into a new read-only skill.

  • Memory. A five-turn working memory, so "summarise that" or "open it" refers to the right thing.

One funny lesson from this period: a bug I spent ages chasing turned out to be an old server process still running from a previous version. Now the app checks that the code it's serving is current.

Version 0.8: thinking without a model

The next problem was requests that no single skill covers, like "find all my text notes, then save a combined report". Instead of reaching for a language model, I added a small planner inspired by active inference. It keeps a tiny model of states (files listed, text extracted, summary ready, file written), works backwards to find the shortest safe chain of basic actions, and simulates it before running anything. If the plan works, it's saved and replayed as a reflex next time. If I cancel it, that path is weakened so it picks a different one.

Version 1.x: safety first, then the "brain" parts

Once NSEE could change files in bigger ways, I wanted a guarantee that a half-finished task could never leave a mess. Every file operation is now previewed as reversible, recoverable or irreversible, and a journal saves a copy of everything before it's touched.

Then came the parts closest to the original brain idea:

  • A Wernicke-style comprehension module that reads a sentence into a frame (what's being asked, about what, with which negations), plus a Broca-style module that writes the reply.

  • Neural assemblies: a small leaky integrate-and-fire circuit per request, where a capability "wins" when its neurons fire together across regions.

  • Neuromodulators: dopamine scales how fast connections change, and a serotonin-like "risk" signal raises the firing threshold of neurons tied to irreversible actions.

  • A "correct me" loop: if it isn't confident, it states its best guess and asks. If you say "no, I meant…", the wrong connections are weakened four times faster than normal and the right ones strengthened, so one correction actually changes its behaviour.

It also learned to solve small logic puzzles, like "Alice, Bob and Carol each take one shift…", with a step-by-step proof.

The bottleneck: understanding people

By now the engine could do a lot once it knew what you wanted. Getting there was the hard part. People write half sentences, typos, vague instructions and things that only make sense in context. Turning that into a clean, structured request is exactly what large language models are good at, and what rules struggle with.

So I made a compromise. I added an optional small language model (135M parameters, about 100 MB) as a translator: it could suggest a structured version of your request and rephrase results the engine had already checked. It was never allowed to touch the computer, and it could only add negations, never remove them. I even had it running in a hosted web version for a while.

Then I measured everything honestly

When I sat down to write the project up properly, I made one rule: every number must come from a script I can re-run, and every claim must be compared against something simple. That changed the story a lot.

  • The small language model didn't work in its role. Asked to return structured output, it succeeded 0 times out of 12, and it sometimes invented facts. The system stayed safe because it falls back to its own writer, but the model wasn't adding real value.

  • The spiking arbiter wasn't changing decisions. On 60 labelled requests it made exactly the same choices as a plain "does this request mention the right thing?" check. That was hard to accept, but it's true.

  • Natural negation was weaker than I thought. On templated sentences it caught 140 of 150 negations, but on natural ones like "no renaming" or "leave the logs alone", only 28 of 50.

  • Writing hit a wall. An early version padded essays with repeated sentences. When I made it honest (only use real source text), it simply couldn't write more than its sources contained.

How I improvised

Some failures I could fix, and they taught me the most.

The best example is antennas. My first antenna skill only knew microstrip patches, so a request for a dipole silently got patch dimensions, which is the worst kind of error. Instead of writing antenna code, I replaced it with one skill file covering six antenna types (patch, dipole, monopole, helix, Yagi and horn) using standard textbook formulas, plus an Ansys HFSS script for each. I also taught it messy input like "patch 5.8G" or "desing a dipole at 433 mhz". All 16 casual requests I tried came out right, and the horn design matches the worked example in Balanis' antenna textbook.

Testing it on unseen requests then exposed a new bug: antenna types it doesn't support, like Vivaldi or bowtie, were still getting patch dimensions. The fix was simple and general: a skill can now say "only run me if you recognised one of my types". After that, NSEE handled 44 of 48 unseen requests correctly, against 22 for a keyword-matching baseline.

Even while making the figures for this post, I found one more real bug: on Windows, saving the rollback journal sometimes failed because antivirus briefly locked the file. NSEE did the right thing and rolled everything back, but it shouldn't fail at all, so it now retries briefly.

So I ended up with a working experimental direction, not a replacement for real AI assistants. In the end I also pulled back the hosted app. NSEE now lives as an open-source repository with its raw results and a full list of limitations, which feels like the honest home for it.

What I learned

Making an AI system small turned out not to be the hardest part. The hard part is deciding what intelligence actually needs to be there: what can be written as rules, what can live in specialised skills, and where a language model is genuinely needed.

Maybe edge AI doesn't have to be a choice between a giant model and pure rules. There may be room for hybrids: a small, safe, local core that does the work, with language understanding added only where it earns its place.

The bigger lesson was about honesty. Measuring my own claims, and comparing them against something simple, killed a few ideas I liked. It also showed me exactly where to go next, and that feels more valuable than a nicer-looking result.

And then there's communication

That brings me to the other half of my original thought. If AI is becoming a lifeline, communication is the infrastructure that lets that lifeline exist at all. More on that soon.
